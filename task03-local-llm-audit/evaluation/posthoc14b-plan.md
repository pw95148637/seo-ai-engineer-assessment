# 凍結後的事後分析（14B）：預先登錄的計畫

- 寫成時間：2026-10-17T05:50Z（台灣 10/17 13:50），在撰寫 Notebook 與執行任何實驗之前。
- 性質：凍結後的事後分析。凍結系統（`soulo-work03-v3b-train` 的鎖 `8ab9b7ae…`）與它在 8 筆測試資料上的結果都不變；本分析的結果不論好壞，都不用來調整 prompt、知識卡、模型、微調權重或任何凍結檔案，也不改寫既有的判定與指標。
- 執行位置：新的私有 Kaggle kernel `pw95148637/soulo-work03-posthoc-14b`。不 push `soulo-work03-v3b-train`、`soulo-work03-v3-eval`、`soulo-work03-posthoc-fp16`。
- 本檔的 sha256 寫進 Notebook，用來證明計畫早於執行。

## 要回答的問題

YMYL 依主題過度標記，是 Qwen3-8B 能力不足，還是 prompt 或任務框架的問題。做法是同一個凍結 prompt 換成更大的 Qwen3-14B，其他條件不變，看過度標記會不會消失。

已知的背景：prompt 已明文寫「只是談到貸款、賭博、法律等高風險主題……也不是YMYL_RISK」，8B 在 4-bit 有微調、4-bit 無微調、16 位元無微調三種設定下都仍依主題標記（主判讀沒有 YMYL 的 6 筆分別標 4、4、3 筆）。

## 設定

- 模型：`Qwen/Qwen3-14B`，revision `40c069824f4251a91eefaf281ebe4c544efd3e18`（Apache 2.0，權重約 29.6 GB）。
- 載入：和凍結系統相同的 4-bit 設定（nf4、double quant、fp16 運算、權重 dtype fp16、整個模型放在單張 T4）。做法是直接呼叫凍結 bundle 的 `load(adapter=False)`，只把它讀到的 `model_id` 與 `model_revision` 換成 14B；不載入微調權重（8B 的 LoRA 不適用 14B）。
- 其餘全部從凍結 bundle 匯入、不修改：system prompt、知識卡、`messages`、`generate`（greedy 解碼、`max_new_tokens` 768、關閉思考模式）、`audit_one`（最多重寫一次）、輸出契約（`audit_io.py`）。開跑前以凍結的 `check-freeze` 核對 34 個檔案。
- 讀測試資料之前先做環境檢查：記錄磁碟空間、14B 與 8B tokenizer 的 chat template 是否相同；用一篇訓練文章的完整 prompt 做一次前向計算，確認輸出的 logits 都是有限值（排除 fp16 溢位）。通過後才以雜湊 `818b491f…` 核對並讀取 8 筆測試資料。
- 主要比較對象：既有的「8B、4-bit、無微調」輸出（`holdout_base.jsonl`）。兩者的 prompt、解碼、量化與重寫規則相同，只差模型大小。8B 16 位元無微調（`soulo-work03-posthoc-fp16`）與凍結的 8B 4-bit 有微調只作參照。

## 指標

全部由程式依既有參考判斷（`evaluation/holdout8-reference.jsonl`）的主判讀計算，比對函式沿用 `compare_holdout.py`，不新增人工或 AI 判定。

1. **主要指標**：主判讀沒有 YMYL 的 6 筆（ID 12、3、17、8、9、4）中，被標 `YMYL_RISK` 的筆數（/6）。
2. **防護條件**：ID 2（保證獲利）仍標 `YMYL_RISK`；ID 1 標 `YMYL_RISK` 或 `UNSUPPORTED_CLAIM`（主判讀或替代判讀的代碼）。用來排除「YMYL 整體標得少」冒充「分辨能力變好」。
3. 標 `YMYL_RISK` 的總筆數（/8）。
4. JSON 第一次與重寫後符合格式的筆數。
5. 代碼集合與主判讀完全相同的筆數（/8）；應標代碼全數抓到（/6）。
6. 嚴重度：最高嚴重度與主判讀一致（/8）、高於主判讀（/8）。
7. 分數：落在主判讀區間（/8）、落在主判讀或替代判讀區間（/8）、與主判讀典型分數的平均絕對誤差。
8. 原題檢核點：ID 4、9 是否標 `SEO_FALSE`；ID 3 是否標 `STUFFING`；ID 12 是否標 `EXPERIENCE_UNVERIFIED`。
9. 三個典型錯誤的檢核點：ID 3（關鍵字堆疊）是否標 `STUFFING`、是否標 `YMYL_RISK`；ID 17（反詐提醒的否定句）與 ID 8（正確的申請文件說明）是否標 `YMYL_RISK`、最高嚴重度是否為 minor 以下（參考判斷：無缺失或最多 minor）。另節錄 14B 在這三筆的引句、說明與建議原文，只作描述。
10. 與 8B 4-bit 無微調的一致度：代碼集合相同、最高嚴重度相同的筆數（/8）；兩者每筆第一次生成的輸入 token 數是否相同（確認 prompt 一致）。

## 預期方向與理由

預期 14B 仍會過度標記，但比 8B 少：主要指標 2 到 3 筆。乾淨樣本 ID 8、17 較可能不再被標，賭博情境的 ID 12、3 較可能仍被標。

理由：ID 8 把正確說明當風險、ID 17 把「絕不會詢問您的驗證碼」讀成否認風險，屬於讀懂文意的錯誤，較大的模型通常較少犯；ID 12、3 是賭博情境，prompt 的「引導讀者實際參與可能違法的活動」一條可以被放寬解讀，加上 YMYL 在 Google 的品質評分指南中本來就是主題類別，這兩筆的標記較可能來自定義與框架，不隨模型變大而消失。

## 判讀規則

只有 8 筆，只看方向，不做顯著性推論。

- 主要指標 ≥3/6：寫成「**14B 仍依主題多標**：模型從 8B 換成 14B，在這 8 筆上沒有消除 YMYL 過度標記；原因較可能在 prompt 或任務框架，而不只是 8B 能力不足。更大的模型或改寫框架是否有效，這次沒有驗證。」
- 主要指標 ≤1/6 且防護條件成立：寫成「**明顯改善**：同一個 prompt，14B 分得出談到高風險主題與作出有害說法；在這 8 筆上，8B 的過度標記主要來自模型能力不足，prompt 的定義足以讓較大的模型照做。」
- 主要指標 ≤1/6 但防護條件不成立：寫成「YMYL 整體標得較少，不能算分辨能力變好；方向不明確。」
- 主要指標剛好 2/6：寫成「方向不明確」，並照實寫出是哪 2 筆。
- 無論落在哪一條，都另外描述被標的是哪幾筆：乾淨樣本（ID 8、17）與賭博情境中另有缺失的文章（ID 12、3）分開寫。乾淨樣本不再被標、賭博情境仍被標，寫成「讀錯文意的錯誤減少，剩下的集中在賭博情境」；這段只是描述，不改變上面的判讀。
- 嚴重度另外照實報告「高於主判讀」的筆數，不另設門檻。

## 執行失敗的處理

- 讀測試資料之前的失敗（下載、磁碟、載入時記憶體不足、logits 檢查不通過）：測試資料還沒讀，只修正與記憶體或環境有關的部分後在同一個新 kernel 重跑，修正內容記在結果檔。若必須改變載入設定（例如 fp16 溢位而改運算精度），屬於偏離計畫，照實寫進結果檔。
- 讀測試資料之後因記憶體或環境錯誤中斷：只修正記憶體或環境設定，用同一套程式完整重跑 8 筆，兩次的輸出都保留並在結果檔說明。
- JSON 不合格、內容不理想都不重跑，照實記錄。
