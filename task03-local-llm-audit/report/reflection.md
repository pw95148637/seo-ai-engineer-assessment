# 技術反思：Qwen3-8B 的中文 SEO 診斷與提示詞改善

**結論**：提示詞讓 JSON 輸出穩定、嚴重案例判對，模型也辨識出錯誤 SEO 理論與未驗證經驗；但 8B 模型分不清「談到高風險主題」與「文章本身有缺失」，12 筆、9 步的 LoRA 也沒有改變這一點。

## 選 Qwen3-8B 的理由與代價

原題允許同級模型。選 Qwen3-8B 的理由：中文語料多，preflight 即能寫出繁體中文；Apache 2.0，不需申請授權即可在 Kaggle 從 Hugging Face 下載；chat template 支援 system role（Gemma-2 不支援，複雜 system prompt 得併入 user 訊息）；原生 context 32K，容得下約 1,900 tokens 的 prompt 加知識卡。代價有三項。第一，沒有在同一資料上實測 Llama-3-8B 或 Gemma-2-9B，上述比較依公開規格，不是對照實驗。第二，用語偏中國大陸：holdout 的 adapter 理由與建議中有 5 處「質量、搜索、用戶、鏈接」（台灣用品質、搜尋、使用者、連結）；簡體字與中國法律用語為 0，引用的台灣法條內容也正確，但刑法 266 條常被套到不相干的句子，例如反詐提醒。第三，為了只輸出 JSON 而關閉 Qwen3 的思考模式，模型沒有顯式推理步驟，改以「理由先於分數」的鍵順序補足。

## 提示詞迭代（只用 train12）

- **v1**：ID 14 三溫度 JSON 3/3 有效，但三次都把沒有自述的文章標成未驗證經驗，單一原因最多貼 5 張卡，嚴重案例給 55–59 分，其中一次建議避免使用「風險」字眼。
- **v2**：限定經驗代碼只用於第一人稱自述、禁止建議刪除風險揭露、每原因最多 2 張卡。虛構經驗、來源堆疊、跨領域法條全部消失；但 train12 分數只剩 25／55／85 三檔，ID 14、7 給 55。讀原始輸出推斷原因：Score 是第一個生成的鍵，模型在寫出任何理由之前就決定了分數。
- **v3／v3b**：鍵順序改為理由→分數→建議，每個理由帶 severity，分數必須落在最高 severity 的區間，不符就退回模型重寫一次，程式不改分。v3 在訓練第 0 步 OOM（prompt 變長，計算全序列 logits 時再要求 1.11 GiB 超出 T4 顯存），v3b 只改記憶體寫法，loss 的數學定義不變。分數變成 0 到 50 的五種值，ID 14 三溫度皆 0 分、建議方向一致。代價是等級膨脹：train12 分數平均絕對誤差由 v2 的 16.6 升到 31.9。v3 同時改了 prompt、監督格式與訓練步數，不是單一變因的實驗。
- **檢查器誤判**：v3b 有兩句「避免否認或淡化法律風險，例如增加說明……」被自動檢查判成刪除風險揭露，原因是規則沒涵蓋並列動詞。修正後凍結選擇不變，holdout 的 21 句建議在新舊檢查器下判定相同。v3b 仍未通過 train gate，依事前停損規則凍結。

## LoRA 幾乎無效

v1、v2、v3b 三個版本的平均 train loss 都在 2.30–2.53 之間（v3b 三個 epoch 的逐步 loss 平均依序約 2.51、2.26、2.11，見 `training.json`）；輸出仍是縮排 JSON（holdout 8/8），監督答案則是緊湊 JSON。adapter 在自己訓練過的 12 筆上也沒學會：ID 10 標註 74 分、輸出 0 分；ID 20 標註 95 分、輸出 50 分；ID 5 漏標自述經驗，base 反而抓到（`baseline_comparison.json`）。學習率刻意維持 1e-4：調高會讓 in-sample gate 靠背誦通過（`run_config.json` 的 status）。holdout 上 adapter 與同 prompt 無 adapter 的代碼集合 6/8 相同、severity 7/8 相同；判定 adapter 3 準確、2 部分準確、3 偏差，base 2、3、3，差在 ID 2；分數平均絕對誤差反而是 base 較低（21.3 對 27.0）。這個對照只排除了 LoRA 的貢獻：行為由 base 模型加上 prompt 決定，知識卡沒有做消融，不能單獨歸功。LoRA 為何無效分不出主因：12 筆資料、9 步、學習率 1e-4、平均 train loss 2.30 而且連緊湊格式都沒學會，這幾個因素混在一起。

## 凍結後的事後分析

依先存檔的計畫（`evaluation/posthoc-plan.md`）另跑 kernel `soulo-work03-posthoc-fp16`，結果在 `evaluation/posthoc-results.md`：16 位元、不載 adapter 時，參考主判讀沒有 YMYL 的 6 筆仍標 3 筆（4-bit base 為 4 筆），剛好在事前門檻上，判讀為 YMYL 過度標記不是 4-bit 量化造成；train12 監督答案的交叉熵在載入 adapter 後由 2.628 降到 2.086，但這是訓練資料，判斷仍然錯。兩項都只看方向，不回頭調整凍結系統。

## 仍存在的偏差與下一步

8 筆中，參考判斷沒有 YMYL 的 6 筆有 4 筆被標 YMYL，兩筆乾淨樣本都被扣到 major；7 筆 severity 高於參考主判讀；47 字重複 5 次「娛樂城推薦」的 ID 3 沒被標堆疊；ID 17 把「正規客服絕不會詢問驗證碼」讀成否認風險。依主題標 YMYL、把引導參與判成 critical，都違反 prompt 已寫明的規則，顯示對 8B 模型再加長規則的效果有限。下一步：

1. 用規則先抽出關鍵字密度、保證詞、第一人稱自述等訊號，模型只判斷被標出的句子；
2. 設定代碼對應的 severity 上限，例如錯誤 SEO 理論預設 major；
3. 先累積數十筆人工標註，尤其是乾淨樣本與邊界案例，再評估微調，並保留 train 內部驗證集。

## train／holdout 分離

20 筆以 seed 42 固定切成 12／8，雜湊記錄在 split-manifest。prompt、知識卡、監督答案與停損規則只依 train12 制定；train kernel 開頭檢查未掛載 holdout。凍結後才產生 eval Notebook，Kaggle 上逐檔核對 34 個凍結檔（31 個與鎖相同，3 個是事先宣告雜湊的量測程式變更）及 holdout 雜湊後才讀取 8 筆。參考判斷在看到模型輸出前完成。限制：資料切分前核對來源時曾看過 20 筆原文，但未用於標註或調整。
