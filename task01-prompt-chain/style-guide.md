# 寫作準則

這條鏈的所有產出都會被人讀：搜尋的玩家讀文章，公司讀交付文件，接手的人讀系統文件。共同標準是讀者讀一次就能理解並據以行動；要讀者自行推算、回查或追問的地方都是缺陷。寫作、編輯、審核與盲評都用這份準則。

## 一、共通

1. **讀者需要的先寫。** 結論或建議先講，原因與條件隨後，細節最後。
2. **具體到能核對。** 數字、條文、畫面上的字、步驟，寫成讀者能自己比對的值；確定的、推測的、不知道的分開寫。
3. **精簡。** 刪到再刪就會讓讀者誤判或追問為止。不寫查證過程、寫作方法與自我辯護。
4. **用讀者的詞。** 玩家說「流水」「出金」「帶單」，就不改寫成「投注量要求」「提領」；同一個概念全文同一個詞；術語第一次出現時用一句白話解釋。
5. **沒有 AI 腔。** 判準是一般人會不會這樣講。常見的有：預告句（「接下來我們來看」）、總結句（「總而言之」）、對稱排比、金句與比喻堆疊、連續破折號的長句、(a)(b) 條列腔、每段重複的免責聲明、行銷語氣、驚嘆號與 emoji。
6. **警語放在用得到的地方。** 法律與金錢風險的提醒，放在讀者要做決定的那一段，不集中成一段說教。

## 二、對外文章（玩家心得）

讀者是正在考慮要不要做某個決定的台灣玩家。目標是讀起來像一位有實際經驗、講話直接的老玩家在論壇分享，而不是業配、新聞稿、查核報告或小說。

- **口語但完整。** 句子可以短、可以用玩家口吻，但每句話有資訊量；不為了像真人而硬塞語助詞。
- **第一人稱只寫做過的事。** 經歷、金額、次數、年資照作者原話，不補細節、不升級。沒做過的就說沒做過，講一次，然後用別人的公開經驗或規則接下去。
- **別人的經驗要標清楚是誰的。** 兩種寫法：
  - 第三方案例：一位真實發文者的經歷，交代出處（例如「PTT 有一篇……」），細節照原文。
  - 綜合重建：把幾個真實來源描述的同一種流程組成一個情境，開頭一句說明「以下依……整理，不是某一個人的經歷」。情境裡的金額、天數、對話都要對得到來源；為了算給讀者看而設的數字，標明是假設。
- **限制講一次就好。** 揭露放在開頭與結尾各一句；正文不在每段重複「我不是專家」「以上僅供參考」。
- **出處要讓讀者能查，不必講查的過程。** 正文寫「165 的宣導寫……」「刑法第 266 條……」。文末資料來源是給讀者查證用的：每條來源寫名稱、日期、連結，必要時一句說明它支撐哪個說法；取材說明只寫讀者需要知道的（哪些是作者經驗、哪些是推論、哪些數字無法公開查證、條文查核到哪一天）。製作過程不寫進文章，包括內部代號、哪一步核對、用什麼工具抓取、作者哪天確認了什麼，這些留在執行紀錄。
- **法條寫條號加白話。** 只有讀者需要逐字看的短句才加引號引原文；長條文改寫成白話並保留條號，原文放資料來源。
- **免責只在開頭與結尾。** 正文其他地方不加「以下不是法律意見」這類句子，需要的併入開頭揭露。
- **評論有標準。** 先說用什麼標準評，優點附條件，缺點附證據；作者自己的看法寫成看法，證據不支持就照實改口。
- **感官細節點到為止。** 一兩句畫面上的字、等待的感覺、數字跳動，來自真實經驗或來源；不鋪陳場景、不寫心理描寫的形容詞堆疊。
- **算給讀者看。** 簡單算術（加減乘除、打平點、期望值）在正文寫出假設、算式、結果，一行一步。統計推導（信賴區間、常態近似、公式推導）正文只寫結論與白話，算式放文末「本文的計算與假設」，讓想重算的人查得到。

## 三、交付文件與簡報（給公司）

- 每份文件第一段寫它回答什麼、結論是什麼。
- 成果寫成「之前 → 之後 → 帶來的價值」，數字附出處。
- 比較與結果優先用表格，說明一行內講完；個人判斷明確標示。
- 不利的結果照實寫，用陳述事實的口吻，不用檢討或懺悔的口吻。
- 簡報標題是講者唸得出口的一句話；每頁少量重點，細節放講者備忘稿。

## 四、系統文件（README、SKILL、prompt）

- 寫現況：不寫「原本……改為……」與事件經過，版本差異只記在 `SYSTEM_CHANGELOG.md`。
- 不用「本輪」「此次」這類需要對話脈絡才懂的指涉；給 subagent 的內容要能獨立成立。
- 用既有詞彙，不自創術語。本專案固定用詞：
  - 主控：執行這條鏈的主對話（orchestrator），負責派 subagent、做關卡判斷。
  - 關卡：每一步的通過條件。
  - 下一步決定：讀者讀完要做的那個決定，用來區分兩個微意圖是否不同。
  - 代號：證據包裡每條來源的編號（例如 R2-a）。
  - 綜合重建：見「二、對外文章」。
  - 對照組 1：只給題目的單一 prompt。對照組 2：給相同資料與準則的單一 prompt。盲評：評審不知道哪篇是怎麼產生的評分。
