# 迭代紀錄摘要

這份文件回答：這套提示詞鏈改過幾版、每次為什麼改、誰提出、改了之後有沒有變好。原題要求的「迭代紀錄」是完整對話歷史，連結另附；這份是導讀。完整的逐項紀錄在 `SYSTEM_CHANGELOG.md`，每次執行的過程在 `outputs-v1/`、`outputs-v3/`、`outputs/` 的 `run-log.md`，各自附當時的系統快照。

結論：
- 系統從 v1 改到 v4，**每一項改動都對得到一份產出裡的具體問題**，來源包括作者的意見、盲評、審核紀錄與獨立審查。
- 改善最明確的是**可信度與讀者安全**：虛構經驗、事實錯誤、權威來源、行動步驟都有可數的進步。
- **真人感改了三次措辭都沒動，改了「誰來讀」才動。** v3 的四個定稿版本 12 位評審都給 3 分；v4 讓一位不拿來源的審核者用讀者眼光讀，真人感到 3.7。
- **最後兩次迭代回答了「是不是根本不需要長鏈」**：寫作步驟可以省，全文複審不能省；審核依錯誤類型分頭做，以約一半的成本（送評版相比）達到接近上一版的品質。

## 3. 是不是根本不需要長鏈：兩次實驗

作者質疑：鏈的機制理論上應該好，結果卻只比單一 prompt 好一點、成本高很多，是設計不好，還是任務本身不需要完整長鏈？

**先拆成本。** 依 API 牌價（含快取折扣）換算，v3 完整鏈到第 4 輪送評版約 US$31.5，審核與三輪全文複審合計 US$14.0，因為每輪都重開十幾個網頁、重讀全部來源。

**實驗一：精簡鏈（v3.4）。** 同樣資料與準則，寫作一次 → 獨立審核 → 修正兼顧口吻 → 只驗修改處。三組拿到相同的作者經驗，三位新評審盲評並數缺陷：

| | v3 完整鏈 | 精簡鏈 | 同資料單一 prompt |
|---|---|---|---|
| 總分（滿分 25） | 23.0 | 21.3 | 21.3 |
| 評審列出的缺陷數 | 1.0 | 1.7 | 2.3 |
| 真人感 | 3.0 | 3.7 | 4.0 |
| 成本 | US$31.5 | US$7.9 | US$2.8 |

結論：寫作步驟可以省（精簡鏈只寫一次，真人感反而較好）；全文複審不能省（三位評審都抓到精簡鏈同一個缺陷：審核抓到了，修正只改一半，只驗修改處沒擋下）。

**實驗二：v4 驗證。** 依實驗一推出 v4，加上作者提議的分角度審核，實際跑一次，和 v3 定稿、重跑的單一 prompt 一起交給三位新評審：

| | v4 鏈 | v3 完整鏈 | 同資料單一 prompt |
|---|---|---|---|
| 總分（滿分 25） | 22.3 | 22.7 | 19.0 |
| 評審列出的缺陷數 | 1.3（3 條都成立） | 1.3（1 條成立，屬 v3 寫作後才確認的作者偏好） | 3.7 |
| 真人感 | 3.7 | 2.7 | 3.3 |
| 成本（到送評版） | US$16.6 | US$31.5 | US$2.1 |

結論：v4 以約一半的成本達到接近 v3 的品質，口吻更好。v3 的定稿吸收過四輪盲評回饋，v4 送評前沒有任何外部回饋；v4 被列的 3 條缺陷都是一兩句的說太滿或漏提醒，一輪盲評加小修就補上。SKILL 預設改用 v4。

限制：每組只跑一篇；評審與寫作者是同一個模型家族；總分差距在評審之間的差異內。

## 4. 還沒解決的

**真人感還不到 4。** 各版本完整鏈的真人感：

| 版本 | 針對真人感做的事 | 真人感 | 評審扣分的理由 |
|---|---|---|---|
| v3.1 | 查證說明移到文末 | 3 | 正文有查證聲明、揭露重複三次、條號與條文原文堆疊 |
| v3.2 | 口吻編輯：刪查證聲明、揭露只留首尾、長條文改白話 | 3 | 資料來源段洩漏製作過程、統計算式在正文 |
| v3.3 | 資料來源只寫讀者需要的、統計推導移到文末 | 3 | 條號清單、九步善後、官方說法逐條對照 |
| v3.4 | 加入作者補充的澳門現場 | 3 | 後半的條號與九步善後像官方手冊 |
| v4 | 寫作一次；讀者視角審核不給來源 | 3.7 | 後半的帳戶分類、法條、文末計算；少數整理腔（已修） |

措辭層的問題一路修掉，剩下的是內容本身：一篇文章同時回答「能不能信」與「已經出事怎麼辦」，後者為了讀者安全必須有條號、管道與步驟。下一版要在選題時就把善後拆成另一篇（對應「帳戶被限制」「會不會被抓」兩個意圖），用內部連結串起。

**讀起來有力的概括句最容易逃過檢查。** v4 開頭「帶單群最後要的通常……是你的帳密」說得比來源重，三份審核與全文複審都沒抓到，讀者視角審核甚至把它列為「不要改掉」的段落；最後是盲評評審抓到的。下一版要讓正確性審核專門檢查開頭與小結的概括。

## 5. 迭代的方法

每一次改動都照同一個循環：
1. **跑完自評。** 找出最影響品質的問題。
2. **追根因。** 追到是哪個 prompt、關卡或工具造成的，而不是只修這一篇文章。
3. **改系統並記錄。** 在 `SYSTEM_CHANGELOG.md` 記下改了什麼、為什麼、依據哪份產出。
4. **再量一次。** 舊產出改名保留、附上當時的系統快照，讓前後可以比較；量不準就改量法（例如加缺陷計數、成本改算金額）。

四個例子：
- **審核者的建議本身違反準則。** 審核建議在正文加「以下不是法律意見」，修正照做，盲評扣真人感。改的是「審核建議要符合準則」這條規則，而不是只刪那一句。
- **引文檢查原來是循環驗證。** 拿修正紀錄當引文來源，等於用文章自己的句子證明自己。用舊產出實測，未找到出處的引文從 5 條變成 0 條，才確認問題；改成只認來源原文摘錄。
- **錯誤的源頭在證據檔。** 「刑事局那一章沒有提到博弈」被寫進文章、兩輪複審都沒抓到，源頭是來源摘錄裡一行錯誤說明。除了修文章，也在摘錄檔加註更正，避免下一次執行再犯。
- **口吻問題要換讀者，不是多改幾次。** v3 三次針對口吻的修改都沒讓真人感變動，而口吻問題每次都是盲評評審抓到的。v4 因此讓一位審核者刻意不拿來源，真人感第一次上升。
